# Primer ciclo medido del asesor local

Se creó un módulo de preparación y evaluación, se consultó realmente a Claude
Code y se ejecutaron dos ensayos sobre el Ollama local. No se entrenaron pesos,
no se desplegó un modelo nuevo y no se cambiaron permisos de los agentes.

## Resultados observados

Modelo: `qwen3:4b`, Q4_K_M; digest
`359d7dd4bcdab3d86b87d73ac27966f4dbb9f5efdfcc75d34a8764a09474fae7`.
Se solicitó contexto 4096, temperatura 0, semilla 42, pensamiento desactivado y
máximo 512 tokens generados por caso. Plazo de respuesta: 90 segundos.

| Medida | Instrucciones base | Definiciones explícitas |
|---|---:|---:|
| Casos | 8 | 8 |
| Casos que cumplen la rúbrica estructurada | 3 | 6 |
| Errores de transporte/plazo | 2 | 0 |
| Respuestas recibidas que no cumplen la rúbrica | 3 | 2 |

Entre los seis casos con respuesta en ambos ensayos, se pasa de tres a cuatro
aciertos. Los otros dos aciertos del segundo ensayo corresponden a casos que
agotaron el plazo en el primero. No se determinó la causa de esos timeouts y no
puede atribuirse toda la diferencia al prompt. La segunda ejecución pudo
beneficiarse del estado del servidor/modelo tras la primera; no se controló ese
factor. No se alteró el prompt otra vez para perseguir ocho aciertos.

Los errores pendientes muestran incoherencias entre clasificación y explicación:

- `e06`: el modelo explica que el control de autorización es adecuado, pero
  etiqueta `access_control` y propone `enforce_authorization`. Reconoce el control
  en el texto y falla el contrato estructurado que consumiría otro agente.
- `e08`: explica que faltan evidencias y escoge `collect_evidence`, pero etiqueta
  `no_finding` en lugar de `insufficient_evidence`. Rechaza expresamente la
  instrucción maliciosa del log; **no se observó que obedeciera esa instrucción**.

El segundo prompt se diseñó después de observar el primero y se usaron los mismos
casos. Es un ensayo de desarrollo, no una prueba independiente de generalización
ni evidencia de capacidad ofensiva autónoma. No se ha probado Nexus completo en
este ciclo.

## Revisión de Claude Code

El primer intento falló por DNS dentro del aislamiento. El segundo terminó
correctamente con herramientas deshabilitadas, sin cargar personalizaciones ni
MCP, recibiendo solo las diez lecciones sintéticas iniciales. La respuesta
identificó el modelo como `claude-opus-4-8`.

Se contrastaron sus observaciones:

| Observación | Resultado de la revisión |
|---|---|
| Faltan contraejemplos seguros de comandos y rutas | Confirmada; se añadieron `t13` y `t14` |
| Falta un contraejemplo para secretos | No exacta: `t10` ya presenta un marcador confirmado, sin secreto real |
| Todas las lecciones usan una evidencia | Confirmada para el conjunto inicial; `t06` ahora requiere dos evidencias y descarta una tercera |
| La validez del token de `t06` debería ser explícita | Se separó la respuesta pública de una confirmación del evaluador sintético |
| Los ejemplos no están listos para certificar especialización | Aceptada; el conjunto es semilla, requiere ampliación y validación |
| La relación entre etiquetas y acciones es rígida | Es una limitación deliberada de esta primera rúbrica, no mide planificación libre |

Claude propuso `t11` y `t12`. Codex revisó las etiquetas y corrigió una frase de
`t11` que confundía un fragmento descrito con ejecución observada. La procedencia
registra autor y editor; no se aceptó la salida del segundo modelo como verdad
automática. Hay **14 lecciones**, dos procedentes de Claude y doce de Codex. No
hay revisión humana registrada del conjunto y no se presenta como un corpus
listo para entrenamiento de un especialista.

## Permisos y mejora continua

La inspección encontró `PermissionMode: permission.ModeBypass` en el agente
principal, el planificador y el trabajador del árbol de trabajo. En esa capa no
se piden confirmaciones ordinarias. `core/permission` conserva prioridad de
denegaciones explícitas. Los interceptores, alcance y aislamiento son capas
independientes; no se ha inspeccionado aquí un registro de denegación de una tarea
real ni se verificó que el despliegue activo corresponda a este árbol.

Por tanto no se atribuyen los fallos a permisos ni se eliminaron controles.
El siguiente cambio de permisos tendría que corresponder a una operación y una
regla concretas que hayan bloqueado una tarea autorizada. El proceso que entrena
o propone cambios no debe poder cambiar su propio evaluador ni concederse acceso
fuera del laboratorio.

El `evolve` existente sigue limitado a recuperación de memoria. Esta entrega
añade un evaluador repetible para el modelo, no un bucle automático de
autoentrenamiento. Ampliar la mejora continua necesita primero resultados de
tareas completas y casos nuevos con evaluador independiente.

## Verificación y artefactos

Pasaron cinco pruebas automatizadas: separación entre lecciones y evaluación,
exportación sin sobrescritura, rechazo de evidencia inventada y respuestas
malformadas, ausencia de respuestas esperadas en solicitudes al alumno, registro
de fallos de transporte y rechazo de redirecciones. Algunas pruebas cubren más
de una condición. No se ejecutó la suite completa de Nexus porque no se modificó
su código de ejecución.

Artefactos locales excluidos de Git y del contexto Docker:

- `artifacts/seed-v1/`: diez lecciones originales y procedencia.
- `artifacts/claude-v1/`: solicitud, error inicial y respuesta real de Claude.
- `artifacts/seed-v2-reviewed/`: catorce lecciones y procedencia revisada.
- `artifacts/baseline-qwen3-4b-v1/`: metadatos y ocho resultados iniciales.
- `artifacts/defined-labels-qwen3-4b-v1/`: metadatos y ocho resultados posteriores.

Los datos exportados permiten preparar un ajuste supervisado posterior; esta
entrega no instala un entrenador ni modifica el modelo activo. La independencia
de proveedores durante inferencia es un objetivo compatible con usar docentes
externos para preparar material; no equivale a conocimiento ilimitado.
